# Insights

Non-obvious design decisions and discoveries.

## 001 — @auth0/ai-vercel SDK swallows token exchange errors (2026-04-02)

The `@auth0/ai-vercel` SDK's `TokenVaultAuthorizerBase` silently swallows federated connection errors ([auth0-ai-js#175](https://github.com/auth0/auth0-ai-js/issues/175), still open). When the token exchange HTTP call fails, the SDK returns `undefined` instead of throwing — then `validateToken()` throws a misleading `TokenVaultInterrupt` saying "Authorization required" when the real issue may be misconfigured credentials, wrong connection name, or expired refresh token. This made initial Token Vault setup extremely difficult to debug. Fix: call Auth0's `/oauth/token` endpoint directly using Auth0's federated connection access token exchange grant (extends RFC 8693 patterns), which surfaces actual error messages. **Note:** The SDK added AI SDK v6 compatibility in v5.0.0 (Jan 29, 2026) — the version mismatch we initially hit is resolved, but error swallowing remains the primary reason for direct exchange.

## 002 — Google login ≠ Token Vault Connected Accounts (2026-04-02)

Logging in with "Continue with Google" authenticates the user but does NOT store Google's refresh token in Token Vault. The Token Vault needs a separate "Connected Accounts" flow triggered via Auth0's `/auth/connect` endpoint (`enableConnectAccountEndpoint: true`). The connection must be set to purpose "Authentication and Connected Accounts for Token Vault". Additionally, Google only returns a refresh token on first consent — if using Auth0 development keys (which don't request `access_type=offline`), the refresh token is never stored. Must use your own Google OAuth credentials.

## 004 — AI SDK v6 needsApproval supports async functions (2026-04-02)

The `tool()` function in AI SDK v6 accepts `needsApproval` as either a boolean or an async function `(params) => Promise<boolean>`. This enables dynamic approval logic — e.g., approving low-value deals automatically but requiring confirmation for >$50K. The SDK streams an `approval-requested` state to the client, which renders an approval card. The client calls `addToolApprovalResponse({ id, approved })` to proceed. This is superior to CIBA for hackathon demos because the consent happens inline in the chat (judges see it live) rather than on a separate device.

Multiple breaking changes from AI SDK v5 to v6: `parameters` → `inputSchema`, `maxSteps` → `stopWhen: stepCountIs(n)`, `maxTokens` → `maxOutputTokens`, `useChat` no longer has `input`/`handleInputChange`/`handleSubmit` (use `sendMessage` + `status`), `api` option replaced by `transport: new DefaultChatTransport({api})`, and `messages` from client are `UIMessage[]` that need `convertToModelMessages()` before passing to `streamText`.

## 005 — Auth0 Token Vault does NOT support per-request scope restriction (2026-04-03)

Auth0's federated connection access token exchange (`urn:auth0:params:oauth:grant-type:token-exchange:federated-connection-access-token`) does NOT accept a `scope` parameter. Confirmed by Auth0 docs and `@auth0/ai` SDK source code. The response includes `scope` and `expires_in` fields, but you cannot request narrower scopes at exchange time — the full consented scope set is always returned. The `@auth0/ai` SDK uses scopes only for post-exchange validation (throws `TokenVaultInterrupt` if required scopes are missing), never sends them in the exchange request. For least-privilege signaling, implement it at the application layer: tools self-declare minimum required scopes and the UI shows which subset is actually used.

## 006 — MCP server needs same security layers as chat route (2026-04-03)

When adding a new entry point (MCP endpoint alongside the existing chat API), every security layer from the original entry point must be replicated: capability filtering, approval checks, user identity resolution, and audit attribution. The MCP route was initially added with tool registration but without `filterToolsByCapabilities` or `attachApprovalChecks`, creating a bypass for all permission controls. Fix: MCP only exposes read-only tools (approval-required tools excluded since MCP has no interactive approval UI), requires auth, and logs all calls to the audit trail.

## 007 — AI SDK tool objects use `inputSchema` not `parameters` (2026-04-03)

In AI SDK v6, the `tool()` helper returns an object with `{ description, inputSchema, execute }`. The property is `inputSchema` (matching the v6 naming), not `parameters` (which was the v5 name). When building adapters that convert AI SDK tools to other formats (like MCP), inspect the actual runtime shape rather than guessing from memory or type casts.

## 008 — In-memory audit filtering is acceptable at hackathon scale (2026-04-03)

Redis lists (`LRANGE`) do not support field-level filtering — there's no `WHERE toolName = 'x'` equivalent. For a production audit log, you'd use a secondary index (Redis Search, Sorted Sets by timestamp, or a proper database). For a hackathon with a 7-day TTL and max ~500 entries per user, fetching a larger slice from Redis and filtering in-memory is pragmatic: the data fits in a single response, latency is negligible, and it avoids adding a search dependency. The key insight: when filters are active, fetch 4x the requested limit (min 500) to ensure enough candidates survive filtering, then slice the result to the caller's limit.

## 009 — Action queue is stronger than inline approval for "Authorized to Act" narrative (2026-04-03)

The AI SDK's `needsApproval` flow (v0.2.0) interrupts the user mid-conversation with approval cards. This works for single actions, but doesn't scale to "the AI analyzed your pipeline and recommends 5 next steps." A dedicated Action Center page where suggestions are queued, reviewed, and batch-approved is a fundamentally better UX for the hackathon theme: the user sees ALL suggested actions in context, can compare priorities, edit drafts, and approve selectively. This demonstrates that "Authorized to Act" means more than per-tool confirmation — it means giving users a complete picture of what the AI wants to do and letting them curate it.

The Token Vault integration is reusable outside the AI SDK streaming context. The `exchangeToken()` function works in any Next.js API route handler because it reads the Auth0 session cookie (present in all browser-initiated requests). This means action execution from a dedicated page uses the exact same OAuth flow as the chat tools — no separate auth mechanism needed. Auth0's Token Vault exchange (which extends RFC 8693 patterns) is context-agnostic by design.

## 010 — Google and Slack have opposite branding rules for third-party UIs (2026-04-03)

Google *requires* you to use their official multicolor G logo (not a monochrome version) per their Identity branding guidelines. Slack *prohibits* using their octothorpe (#) logo in third-party product UIs per their brand terms of service ("Cannot include Slack assets in your product's user interface"). The correct approach: Google gets the official SVG, Slack gets a text "S" on their brand purple (#4A154B). Both verified against official documentation — Google: developers.google.com/identity/branding-guidelines, Slack: slack.com/terms-of-service/slack-brand.

Similarly, OAuth scopes should follow each provider's own consent screen patterns.

## 011 — Auth0 CIBA endpoints require form-urlencoded, not JSON (2026-04-04)

Auth0's backchannel endpoints (`/bc-authorize` and `/oauth/token` for CIBA grant) require `Content-Type: application/x-www-form-urlencoded` with `URLSearchParams` body encoding. This differs from the Token Vault exchange endpoint (`/oauth/token` for Auth0's federated connection grant) which accepts `application/json`. Verified by reading the `auth0` SDK v4.37 source (`node_modules/auth0/dist/esm/auth/backchannel.js`). The `login_hint` parameter is a JSON string (`{"format":"iss_sub","iss":"https://domain/","sub":"auth0|id"}`) passed as a form field value — double encoding is required. Additionally, `binding_message` is limited to 64 characters per the CIBA spec, and `requested_expiry` acts as a routing switch: <=300s routes to Guardian push, >300s routes to email.

## 012 — CIBA interrupt reuses TokenVaultInterrupt pattern exactly (2026-04-04)

The existing TokenVaultInterrupt pattern (JSON error in tool execution → `parseInterrupt()` in chat-window → specialized card component → `regenerate()` on resolution) works for CIBA without architectural changes. The key insight: throwing a JSON-encoded error from a tool's `execute` function is a generic "interrupt" mechanism, not specific to token vault. CibaInterrupt and TokenVaultInterrupt are just different payloads in the same pattern. The challenge is preventing re-initiation: when `regenerate()` retries the tool, it would initiate a new CIBA request. Solution: Redis-keyed sessions (`ciba:{userId}:{toolName}`) that the wrapper checks before initiating. If an approved session exists, skip CIBA and proceed. Google translates `calendar.readonly` to "See and download any calendar you can access" on their consent screen. Showing raw scope strings like `calendar.readonly` or `channels:read` is a developer-facing anti-pattern — end users don't know what these mean. The fix: maintain a SCOPE_LABELS map with human-readable translations, show the friendly version as primary text, keep the technical scope available via tooltip for transparency.

## 013 — CIBA is designed for server-initiated flows (2026-04-04)

Auth0's CIBA implementation (`/bc-authorize`) does not require a user HTTP session or browser context — it only needs `client_id`, `client_secret`, `login_hint` (userId), and `binding_message`. This makes it ideal for server-initiated consent: a cron job can send a Guardian push notification without the user being in the app. The CIBA access token returned on approval is scoped to `openid` only — it's proof of consent, not an API token. For actual execution (calling Gmail/Slack/Calendar), you still need the user's refresh token stored separately and exchanged via Token Vault. This "CIBA for consent, refresh token for execution" separation is the key architectural insight.

## 014 — Vercel cron requires two-phase design for CIBA polling (2026-04-04)

Vercel serverless functions can't poll for 5+ minutes (CIBA timeout). Solution: separate the initiation (hourly cron sends CIBA push) from polling (per-minute cron checks Auth0, executes on approval). This maps naturally to the CIBA spec's async model. Key constraint: Hobby plan = daily minimum/hourly precision; Pro plan = per-minute. Vercel delivers cron events at-least-once, so idempotency guards (hour-truncated batch IDs, SET NX execution locks) are essential.

## 015 — Batch CIBA beats per-action CIBA for AI agent consent (2026-04-05)

Per-action CIBA (one Guardian push per action) creates notification fatigue. With 5+ pending actions, the user gets bombarded with push notifications. Worse, Auth0 Guardian only processes one CIBA push per user at a time — subsequent pushes are silently queued or overridden. The fix: batch all high/medium priority actions into a single CIBA request. The binding message describes the batch ("DealFlow: 5 actions - 3 email, 2 calendar"), the user approves once, and all actions execute within the CIBA token's expiry window. The token lifetime is the natural execution boundary — time-boxed delegation, not open-ended authorization.

## 016 — CIBA binding_message character restrictions are strict (2026-04-05)

Auth0's CIBA binding message only allows alphanumerics, whitespace, and `+-_.,:#` characters. Email addresses (containing `@`) are rejected with a validation error. This isn't documented prominently — discovered via runtime error. Fix: sanitize with `/[^\w\s+\-_.,:#]/g` and use contact names instead of email addresses in messages. The 64-character limit also requires careful message construction: prioritize action type counts over individual details.

## 017 — useState(initialProps) doesn't re-sync on server refresh (2026-04-05)

React's `useState(initialValue)` only uses the initial value on first mount. When a Next.js server component re-renders via `router.refresh()` and passes new props, client components that stored those props in `useState` won't see the update. This caused the Action Center to show stale statuses after CIBA batch execution — the server had the updated data, but the client's local state was frozen. Fix: add `useEffect(() => setActions(initialActions), [initialActions])` to sync state when server props change.

## 018 — Per-client MCP tool filtering uses two complementary approaches (2026-04-05)

The MCP specification (2025-03-26) defines OAuth 2.1 auth with scopes, and `mcp-handler` v1.1.0 supports `requiredScopes` for handler-level gating. However, **per-client `tools/list` filtering is not in the spec or Auth0's MCP docs**. Two approaches work together: (1) Registration-time filtering via `allowedToolFilter` parameter — when a per-client API key provides an `allowedTools` list, only those tools are registered. (2) Request-time filtering via an override of the SDK's `ListToolsRequestSchema` handler on `server.server.setRequestHandler()` — captures the original handler's output (with Zod → JSON Schema conversion) and filters based on the requesting client's scopes and allowlist. This ensures restricted clients cannot enumerate tools they aren't allowed to call. Execution-layer enforcement (Layer 3) remains as defense-in-depth.

## 019 — AI SDK callbacks swallow errors but not abort signals (2026-04-05)

The Vercel AI SDK's `notify.ts` wraps all callbacks (including `experimental_onToolCallFinish`) in try/catch that silently swallows errors. This means throwing from a callback cannot stop the stream. However, `AbortController.abort()` doesn't throw — it fires a signal synchronously. Calling `abort()` from inside the swallowed callback works because the signal propagates through the merged abort chain independent of the try/catch. Furthermore, server-side abort sends `{ type: 'abort' }` then closes cleanly — the client sees `status: 'ready'` (not error). To show a meaningful error, write an error chunk via `createUIMessageStream`'s writer *before* calling `abort()` — the synchronous enqueue happens on the outer stream controller, independent of the inner streamText stream, guaranteeing delivery before the abort closes the connection.

## 020 — Two-layer rate limiting: surgical vs nuclear (2026-04-05)

Per-tool rate limiting (Layer A) and per-request abort (Layer B) serve fundamentally different purposes. Layer A is surgical — it blocks one tool while letting others continue, and the AI model can adapt by explaining the limit or using alternative tools. Layer B is nuclear — it kills the entire stream. Neither alone is sufficient: Layer A can't stop a model that alternates between different tools (each within its own limit), and Layer B can't catch abuse that spans multiple requests (each under the per-request cap). Together, they cover cross-request patterns (A: Upstash sliding window per user) and within-request runaway loops (B: in-memory counter + AbortController). The Upstash Ratelimit SDK's `ephemeralCache` means repeated rate-limited calls within the same serverless invocation are blocked with zero Redis commands — important for the runaway-loop case where the model might retry a blocked tool 7 times in one request.

## 021 — CIBA unlocks MCP write operations without approval UI (2026-04-05)

MCP is a stateless request-response protocol with no concept of interactive approval cards. The original assumption was that MCP must be read-only because "MCP has no approval UI." But CIBA (Client Initiated Backchannel Authentication) is designed precisely for this scenario — consent on a separate device with no client-side UI required. The MCP handler blocks synchronously while polling for Guardian push approval, then executes the tool with a stored refresh token. This makes MCP a first-class execution context rather than a second-class read-only surface. The combination of CIBA approval as a gate before Token Vault token exchange is novel in the public record — Auth0 documents them as separate pillars, and no official guide, blog post, SDK example (including auth0-ai-js), or hackathon project combines them. Auth0's own reference implementations (Assistant0, Cloudflare Agents Starter) use both features independently. The batch pattern — single CIBA push for batch approval, then Token Vault exchanges for each action, with token expiry as execution boundary — has no documented prior art.

## 022 — Three-surface model maps to IETF AI agent auth delegation patterns (2026-04-05)

The IETF individual draft `draft-klrc-aiagent-auth-01` ("AI Agent Authentication and Authorization", March 30, 2026, co-authored by Nick Steele of OpenAI among others) defines delegation patterns in Section 10.3, including: User Delegates Authorization (10.3.1), Agent Obtains Own Authorization (10.3.2), and Agents Accessed by Systems or Other Agents (10.3.3). Our three surfaces loosely map to these: Chat (user-delegated — user is present, Auth0 session), Action Center (pre-authorized — agent acts on schedule with stored refresh token), MCP (agent-to-agent — external agents invoke tools via API key). Note: this is an individual Internet-Draft, not an adopted IETF working group document — it represents the authors' views, not IETF consensus. Section 10.6 "Human in the Loop" does explicitly name CIBA as a mechanism for step-up agent consent, which aligns with our pattern for write operations. Source: https://datatracker.ietf.org/doc/draft-klrc-aiagent-auth/

## 023 — Surface Policy Registry uses a similar approach to permit.io's tool authorization concept (2026-04-05)

The `SURFACE_POLICIES` registry in `src/lib/surface-policy.ts` uses a tool-level authorization approach conceptually similar to what permit.io describes for their "Secure External Access" perimeter (https://www.permit.io/ai-access-control). Both treat "which tools can be accessed" as a first-class authorization decision — permit.io describes defining permitted actions and assigning capabilities to agent identities; we implement tool filtering per surface and per MCP client. The key difference: permit.io is a dynamic ABAC engine with runtime policy changes; ours are static TypeScript declarations — no external dependency, no runtime call. Per-tool access control is a well-established pattern in API platforms; our contribution is applying it across multiple trust surfaces with layered intersection (surface policy ceiling → per-client policy narrows → user toggles narrow further). Adding a new surface (e.g., "webhook") requires one registry entry, no tool changes. This comparison is limited to permit.io's execution perimeter and does not extend to their other perimeters (prompt filtering, RAG protection, response enforcement), which we don't implement.

## 024 — Bearer tokens without binding: acceptable risk for hackathon scope (2026-04-05)

MCP API keys are pure bearer tokens — whoever possesses the key can use it from any IP or device. The IETF MCP draft recommends DPoP (RFC 9449) or mTLS for token binding, which cryptographically ties a token to the device that requested it and prevents replay from stolen credentials. We chose not to implement binding for three reasons: (1) even most production SaaS APIs (Stripe, GitHub, OpenAI) use unbound bearer tokens today, (2) DPoP requires client-side proof generation which no MCP client SDK supports yet, and (3) our layered security (per-client rate limiting, CIBA consent for writes, per-tool scope filtering, audit trail) limits the blast radius of a stolen key. For production hardening: add IP allowlisting per API key (stored alongside the client policy in Redis), implement DPoP proof validation when MCP client SDKs add support, and consider short-lived API keys with automatic rotation via the existing key rotation endpoint.

## 025 — Graduated oversight follows the same design principles as EU AI Act Article 14 (2026-04-05)

The EU AI Act's Article 14 ("Human Oversight," effective August 2026) requires high-risk AI systems to be designed for "effective oversight by natural persons" commensurate with risk, autonomy, and context. DealFlow's three-level autonomy spectrum (Suggest Only, Auto-Approve, Full Autonomous) with confidence-based routing and CIBA device consent follows this same design principle — layered human oversight proportional to action sensitivity. Important caveat: a sales CRM tool would not be classified as high-risk under the EU AI Act's Annex III categories (which cover biometric identification, critical infrastructure, employment decisions, law enforcement, etc.). We apply these principles voluntarily as a responsible design choice, not because the regulation requires it for this type of tool. The insight: building for user trust and building for regulatory compliance converge on the same design — both start from the premise that AI systems taking real-world actions benefit from human oversight proportional to risk. Confidence-based routing adds the AI's own uncertainty as a routing signal, ensuring low-confidence suggestions always surface for human review.

## 026 — Per-client parameter constraints add intent verification to MCP (2026-04-05)

Binary tool-level access control ("can this client call searchEmails?") doesn't capture intent. A client with searchEmails access can search for anything — there's no semantic constraint on the query parameter. Adding per-client `parameterConstraints` (regex-based, fail-closed) creates a middle layer: the MCP server can enforce that a specific client can only search emails from `@acme.com` domains, or only check calendars for specific date ranges. This is a pragmatic approximation of structured policy models for AI agent authorization (see arXiv:2501.09674 on authenticated delegation and authorized AI agents), implemented as ~10 lines of regex validation in the tool handler. The key trade-off: regex is less expressive than structured policy languages, but it's immediately understandable, requires no policy engine, and covers the most common intent constraints.

## 028 — Separate visualization from input for threshold controls (2026-04-05)

Research across top-tier products (Stripe Radar, Linear, Vercel, Notion) and NNG usability studies revealed a consistent pattern: none use dual-thumb sliders for threshold controls. Dual-thumb sliders have high error rates — users grab the wrong thumb, touch targets overlap on mobile, and the visual metaphor breaks down at narrow zone widths. The winning pattern is "visualization + precise input": a read-only colored bar shows the current state at a glance, while numeric inputs provide exact control. Stripe Radar uses this for fraud risk thresholds. The insight: interactive visualization is a UX anti-pattern for precision controls. When the user needs to set an exact value, give them a number field. When they need to understand the system's behavior, give them a visual summary. Combining both into one draggable element serves neither purpose well.

## 029 — AI SDK approval flow has three independent loop vectors (2026-04-05)

The `needsApproval` + `sendAutomaticallyWhen` approval flow in AI SDK v6 has three independent bug vectors that compound into an infinite loop. **Vector 1 (client-side)**: A hand-rolled `sendAutomaticallyWhen` that checks ALL parts of the last assistant message will re-trigger on old `approval-responded` parts from earlier steps. The SDK exports `lastAssistantMessageIsCompleteWithApprovalResponses` which correctly scopes to the last step using `step-start` boundaries — use it instead. **Vector 2 (message conversion)**: `convertToModelMessages` creates duplicate `tool_use` IDs when processing `approval-responded` parts across multiple request cycles, which Anthropic's API rejects with `tool_use ids must be unique` (vercel/ai#9968). **Vector 3 (model re-proposal)**: After `collectToolApprovals` executes an approved tool, the model can re-propose the same write tool within the same `streamText` call (multiple steps). Each re-proposal triggers another `approval-requested`, creating a new approval card. Fix: check `context.messages` (SDK model-format messages) in both `needsApproval` and `execute` for prior `tool-result` entries. The insight: the approval flow requires defense at three layers — client auto-send scoping, server-side needsApproval dedup, and execute-level re-execution guard. Six PRs attempted single-layer fixes before this was understood. Known SDK issues: vercel/ai#9968, #7683, #10980.

## 027 — Trust calibration: closing the feedback loop without ML (2026-04-05)

The autonomy selector (Levels 1/2/3) is a manual user setting — not ML-driven. The trust stats (approve/dismiss counts per action type) were write-only telemetry: recorded but never consumed for decisions. This gap is visible to any judge who reads the code. The fix is a simple threshold function (`evaluateTrustGraduation`) that checks per-tool stats and recommends upgrading `toolTrust` from `"ask"` to `"always"` when the approval rate exceeds 80% over 5+ decisions. The key design choice: **nudge, never auto-escalate**. The system suggests, the user decides. This aligns with the "Authorized to Act" theme — even the system's own recommendations require explicit human consent. Upgrade-only (no downgrade suggestions) keeps the UX positive and avoids confusing judges with a "block this tool" nudge during demos.

## 031 — AI SDK needsApproval + sendAutomaticallyWhen has an unfixed recursive loop (2026-04-06)

AI SDK v6's `needsApproval` approval card mechanism has an architectural loop bug that persists through at least `ai@6.0.146`. The SDK evaluates `sendAutomaticallyWhen` in three places: `addToolApprovalResponse` (after user clicks Approve), `addToolOutput` (after a tool result is added), and as a tail-call after `makeRequest` completes (line 13271 in `ai/dist/index.mjs`). The third call site creates recursion: request completes → predicate evaluated → if true, `makeRequest` fires again → completes → checks predicate → loops. The built-in `lastAssistantMessageIsCompleteWithApprovalResponses` helper compounds this by treating `output-available` (tool already executed) as a valid state alongside `approval-responded`, so it returns true after execution.

We tried four workaround approaches — all failed: (1) the SDK's built-in helper, (2) a custom state-checking predicate that only fires when `approval-responded` parts haven't progressed to `output-available`, (3) a module-level boolean one-shot gate, and (4) removing `sendAutomaticallyWhen` entirely and using `regenerate()` after approval (this caused the model to re-run the entire multi-step workflow from scratch each time). Multiple open GitHub issues report symptoms of this bug class: vercel/ai#7635, #7717, #9968, #10169, #10980, #11776 — but none identify the three call sites or the tail-call recursion as root cause.

The working fix: disable `needsApproval` for external action tools entirely. The AI already confirms with the user in chat before executing write operations ("Channel: #sales-team, Message: '...'. Does this look good?"), providing equivalent user control without the SDK's broken approval card mechanism. High-value CRM operations (>$50K deals, closed-won) still use CIBA step-up auth, which is a separate mechanism unaffected by this bug. The insight: when a framework's interactive approval mechanism is broken, move consent to a layer you control — either the AI's conversational confirmation (low-stakes) or device-level consent via CIBA (high-stakes). Both bypass the SDK entirely.

## 030 — Per-connection autonomy: additive override > schema migration (2026-04-05)

Making autonomy per-connection (Google gets Auto-Approve, Slack gets Suggest Only) required a data model decision. Replacing the global `autonomyLevel` with a per-connection map would break all existing consumers (cron routes, action routing, chat). Instead: add an optional `connectionAutonomy` field as an override layer. Resolution order: check `connectionAutonomy[connectionId]` first, fall back to global `autonomyLevel`. This "default + override" pattern (same as CSS cascading, GitHub org/repo permissions, Terraform variable precedence) means zero migration, zero breaking changes, and existing users get identical behavior. The insight: for hackathon-scale apps, additive fields with fallback are almost always better than schema migrations — you get the feature without the risk.
