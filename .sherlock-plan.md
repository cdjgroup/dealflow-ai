# Sherlock Plan: CIBA Step-Up Authentication for High-Value Actions
Created: 2026-04-04
Tier: Full Sherlock
Status: COMPLETED
Completed: 2026-04-04

## Design Decisions (from clarification)
- **Binding message format**: Action-focused (e.g., "Approve creating $75,000 deal: Acme Enterprise")
- **Action Center deal value**: Look up from Redis via dealId at execution time (no SuggestedAction schema change)
- **Chat flow order**: Inline approval FIRST, then CIBA push (two-step consent: app-level + device-level)

## Scope Boundaries
- IN SCOPE: CIBA push notification flow for high-value tool calls ($50K+ deals, terminal stage changes)
- IN SCOPE: Chat integration (CibaInterrupt → CibaWaitingCard → poll → regenerate)
- IN SCOPE: Action Center integration (ciba-pending status, server-side CIBA check)
- IN SCOPE: Direct HTTP to Auth0 `/bc-authorize` and `/oauth/token` (CIBA grant)
- IN SCOPE: CIBA session persistence in Redis
- IN SCOPE: Audit trail with CIBA request ID
- OUT OF SCOPE: Replacing existing inline approval flow (CIBA is additive)
- OUT OF SCOPE: Email-based CIBA notifications (Guardian push only for demo)
- OUT OF SCOPE: `@auth0/ai` SDK wrapper integration (incompatible per ADR 001)
- OUT OF SCOPE: CIBA for read-only tools or low-value actions
- OUT OF SCOPE: User settings to configure CIBA threshold (hardcoded $50K for hackathon)

## Architecture Decision
Approach chosen: Pragmatic (Direct HTTP)
Summary: Direct HTTP calls to Auth0 backchannel endpoints, following the established ADR 001 pattern of bypassing `@auth0/ai` SDK wrappers. Clean `src/lib/ciba/` module with full Action Center support.
Rationale: The `@auth0/ai-vercel` wrapper is proven incompatible with AI SDK v6 (ADR 001). The `@auth0/ai` core package has CIBA primitives, but its tool-wrapping pattern (`withAsyncAuthorization()`) likely shares the same incompatibility. Direct HTTP is proven, predictable, and debuggable within the 2-day hackathon timeline. The token-exchange.ts pattern provides an exact template to follow.

### Alternatives Considered
1. **Minimal** — Only chat tools, reuse TokenVaultInterrupt directly, no Action Center. Rejected: weak demo, hacky integration.
2. **SDK-based** — Use `@auth0/ai`'s `withAsyncAuthorization()`. Rejected: high SDK compatibility risk, 2-day deadline doesn't allow for debugging SDK issues.

## Acceptance Criteria

### AC-1: Happy Path — CIBA approval via Guardian push (Chat)
- **Given** a logged-in user with Guardian MFA enrolled on their phone
- **When** the AI agent triggers `createDeal` with `value: 75000`, the user approves the inline approval card, and the server detects CIBA is required
- **Then** Auth0 sends a push notification to the user's Guardian app with a binding message (e.g., "Approve creating $75,000 deal: Acme Enterprise"), the chat displays a CibaWaitingCard with the binding message and a pulsing indicator, and upon phone approval the deal is created and shown in chat

### AC-2: Denial Path — User denies on phone (Chat)
- **Given** a CIBA push notification has been sent for a high-value deal creation
- **When** the user denies the request on their Guardian app (or the request expires after timeout)
- **Then** the CibaWaitingCard shows "Authorization denied" (or "Request timed out"), the tool execution is blocked, and a user-friendly denial message appears in the chat stream

### AC-3: Routine Actions Bypass CIBA
- **Given** a user triggers any tool that does not meet the CIBA threshold (e.g., `sendSlackMessage`, `createDeal` with value $10K)
- **When** the tool call is initiated
- **Then** only the existing inline approval flow is used (no CIBA push notification), and the tool executes immediately upon inline approval

### AC-4: Action Center CIBA Integration
- **Given** a suggested action in the Action Center linked to a deal with value exceeding $50K
- **When** the user clicks "Execute"
- **Then** the action status changes to `ciba-pending`, Auth0 sends a push notification, the action card shows a CIBA waiting state, and upon phone approval the action executes normally; upon denial the status becomes `failed` with message "CIBA authorization denied"

### AC-5: Error — No Guardian Enrollment
- **Given** a user who has NOT enrolled in Guardian MFA attempts a high-value action requiring CIBA
- **When** the server calls Auth0 `/bc-authorize`
- **Then** Auth0 returns an error, the server catches it, and the UI displays: "Device verification requires Auth0 Guardian enrollment" with guidance, without crashing the chat or action flow

### AC-6: CIBA Session Expiry
- **Given** a CIBA request has been initiated and the user has not responded
- **When** the configured expiry time elapses (default 300s for push)
- **Then** the polling endpoint returns `expired` status, the CibaWaitingCard shows "Request expired", and the user can retry the action

## Interface Contracts

```typescript
// === src/lib/ciba/types.ts ===

export type CibaStatus =
  | "pending"    // Push sent, waiting for user
  | "approved"   // User approved on phone
  | "denied"     // User denied on phone
  | "expired"    // Request timed out
  | "error";     // Auth0 API error

export interface CibaSession {
  authReqId: string;
  userId: string;
  bindingMessage: string;
  toolName: string;
  expiresAt: string;    // ISO 8601
  interval: number;     // seconds between polls
  status: CibaStatus;
  createdAt: string;
}

export interface CibaPollResult {
  status: CibaStatus;
  accessToken?: string;  // Only when status === "approved"
  error?: string;        // Present for "error" | "denied"
}

export interface CibaInitiateResponse {
  authReqId: string;
  expiresIn: number;     // seconds
  interval: number;      // polling interval in seconds
  bindingMessage: string;
}

// Client-side interrupt shape (JSON in error.message, same pattern as TokenVaultInterrupt)
export interface CibaInterrupt {
  type: "CibaInterrupt";
  authReqId: string;
  bindingMessage: string;
  expiresIn: number;
  interval: number;
}

// === src/lib/ciba/authorize.ts ===

/** Initiate CIBA request via Auth0 /bc-authorize endpoint */
export async function initiateCiba(
  userId: string,
  bindingMessage: string,
): Promise<CibaInitiateResponse>;

// === src/lib/ciba/poll.ts ===

/** Poll Auth0 /oauth/token for CIBA grant status */
export async function pollCiba(authReqId: string): Promise<CibaPollResult>;

// === src/lib/ciba/should-require.ts ===

/** Pure function: determines if a tool call requires CIBA step-up auth */
export function shouldRequireCiba(
  toolName: string,
  params: Record<string, unknown>,
): boolean;

// === API Routes ===

// POST /api/ciba/initiate
// Request: { bindingMessage: string; toolName: string }
// Response: CibaInitiateResponse
// Error: { error: string }

// GET /api/ciba/status/[authReqId]
// Response: { status: CibaStatus; error?: string }
// Error: { error: string }
```
