# Sherlock Plan: Scheduled Action Review with CIBA Approval

Created: 2026-04-04
Tier: Full Sherlock
Status: APPROVED — Executing

## Scope Boundaries

- IN SCOPE:
  - Schedule preferences UI (checkboxes for 8am/12pm/5pm) on Action Center page
  - User timezone detection and storage
  - Vercel cron job: Phase 1 (initiate CIBA at scheduled hours)
  - Vercel cron job: Phase 2 (poll CIBA, auto-execute on approval)
  - Redis schedule index for efficient user lookup by hour
  - Scheduled CIBA session storage with active index
  - Refresh token storage with AES-256-GCM app-level encryption
  - Executor refactoring: extract token-accepting internal helpers (Option C — Pragmatic)
  - Cron security via CRON_SECRET Bearer token verification
  - Audit trail entries for scheduled executions
  - CIBA denial → revert actions to pending
- OUT OF SCOPE:
  - Notification UI for scheduled execution results (user sees status on next visit)
  - Custom schedule times beyond the three presets
  - Per-action-type scheduling (all pending actions included)
  - Retry logic for failed scheduled executions
  - Application-level rate limiting on cron endpoints (Vercel handles invocation)

## Architecture Decision

Approach chosen: Pragmatic (Option C)
Summary: Refactor `executor.ts` to extract a `token` parameter into the three private functions, add one new public export `executeActionWithToken(action, token)`. No new executor file, zero duplication, minimal diff to existing code. Cron jobs use `exchangeTokenWithRefresh()` with a stored (encrypted) refresh token to obtain short-lived access tokens for Google/Slack APIs.

Rationale: The executor currently calls `exchangeToken()` internally (which requires an HTTP session via `auth0.getSession()`). Cron jobs have no session. Rather than duplicating executor logic, we thread a `token` parameter through the existing private functions. The refresh token is stored in Redis at opt-in time (encrypted with AES-256-GCM) and exchanged at execution time via the existing `exchangeTokenWithRefresh()` function. This follows the textbook "offline access" pattern per RFC 6749/9700. CIBA serves as proof of consent only (its access token is scoped to `openid`, not usable for API calls). Two-phase cron design (initiate hourly, poll every minute) fits Vercel serverless constraints — short-lived functions, no idle waiting.

Key research findings incorporated:
- Vercel cron uses GET method, `Authorization: Bearer <CRON_SECRET>` header (verified via Vercel docs)
- CIBA is explicitly designed for server-initiated flows without user sessions (OIDC CIBA Core 1.0)
- Auth0 binding message: 64 char limit, charset `[a-zA-Z0-9\s+\-_.,:#]` (Auth0-specific enforcement)
- Refresh token rotation DISABLED is correct for background jobs (rotation invalidates on each use)
- App-level AES-256-GCM encryption provides defense-in-depth beyond Upstash at-rest encryption
- Vercel Pro plan required for `* * * * *` poll cron (confirmed)
- Vercel can deliver duplicate cron events — design for idempotency

### Alternatives Considered
1. **Minimal (Option A)** — Duplicate API call logic in a new `scheduled-executor.ts`. Rejected: maintenance burden of two copies of Gmail/Calendar/Slack API calls.
2. **Clean (Option B)** — Same as Pragmatic but with more abstraction. Rejected: no meaningful benefit over Option C for this codebase size.

## Acceptance Criteria

### AC-1: User opts into scheduled review
- **Given** a user is on the Action Center page
- **When** they check the "8:00 AM" checkbox
- **Then** their settings are saved via `PUT /api/settings` with `schedule: { enabled: true, hours: [8], timezone: "<browser IANA timezone>" }`, their userId is added to the `schedule:idx:8` Redis set, and their encrypted refresh token is stored in Redis with 90-day TTL

### AC-2: User opts out of all hours
- **Given** a user has hours [8, 12] selected
- **When** they uncheck both checkboxes
- **Then** `schedule.enabled` becomes `false`, `schedule.hours` becomes `[]`, their userId is removed from `schedule:idx:8` and `schedule:idx:12`, and their stored refresh token is deleted

### AC-3: Phase 1 initiates CIBA for opted-in users at the right hour
- **Given** user A (timezone `America/New_York`, hours [8]) and user B (timezone `Europe/London`, hours [8])
- **When** the initiate cron fires at 12:00 UTC
- **Then** only user A receives a CIBA push (12:00 UTC = 8:00 AM ET), not user B (12:00 UTC = 1:00 PM BST). A `ScheduledCibaSession` is stored. User A's pending actions are marked `ciba-pending`.

### AC-4: Phase 1 skips users with no pending actions
- **Given** user A is opted in for 8:00 AM and has zero pending actions
- **When** the initiate cron fires at the matching hour
- **Then** no CIBA request is initiated, result includes `status: "skipped-no-actions"`

### AC-5: Phase 2 executes all actions on CIBA approval
- **Given** a `ScheduledCibaSession` exists with 3 action IDs, and the user approves the Guardian push
- **When** the poll cron runs and `pollCiba` returns `status: "approved"`
- **Then** all 3 actions execute via `executeActionWithToken`, each transitions `ciba-pending` → `executing` → `sent`, audit entries are written, and the session is removed

### AC-6: Phase 2 handles partial execution failure
- **Given** a batch of 3 actions where action 2 fails (e.g., Slack API error)
- **When** the poll cron processes the batch
- **Then** action 1 is `sent`, action 2 is `failed` with `errorMessage`, action 3 still executes and becomes `sent`. Session is cleaned up.

### AC-7: Phase 2 handles CIBA denial
- **Given** a `ScheduledCibaSession` exists and user denies the Guardian push
- **When** the poll cron runs and `pollCiba` returns `status: "denied"`
- **Then** all linked actions revert to `pending` status (not `failed`), session is removed

### AC-8: Phase 2 handles CIBA expiry
- **Given** a `ScheduledCibaSession` where `expiresAt` has passed with no response
- **When** the poll cron runs
- **Then** all linked actions revert to `pending` status, session is removed

### AC-9: Cron endpoint security
- **Given** a request to `/api/cron/schedule-initiate` without correct `Authorization: Bearer <CRON_SECRET>` header
- **When** the endpoint receives the request
- **Then** it returns 401 Unauthorized

### AC-10: Missing refresh token during execution
- **Given** a user approved a scheduled CIBA but their stored refresh token has expired or been deleted
- **When** the poll cron attempts execution
- **Then** all actions in the batch are marked `failed` with error message, session is cleaned up

### AC-11: Refresh token encryption
- **Given** a user opts into scheduled review
- **When** their refresh token is stored in Redis
- **Then** the stored value is AES-256-GCM encrypted (not plaintext), and can be decrypted with the `TOKEN_ENCRYPTION_KEY` env var

### AC-12: Executor refactoring preserves existing behavior
- **Given** the existing `executeAction()` function is called from the action execute API route (interactive use)
- **When** an action is executed via the normal UI flow
- **Then** behavior is identical to pre-refactor (session-based token exchange, same API calls, same results)

### AC-13: Idempotent cron initiation
- **Given** user A already has a pending `ScheduledCibaSession` for this hour
- **When** the initiate cron fires again (duplicate delivery)
- **Then** the existing session is reused (not duplicated), no second CIBA push is sent

## Interface Contracts

```typescript
// === Settings type extension (src/lib/types/settings.ts) ===
interface UserSettings {
  // ... existing fields ...
  schedule: {
    enabled: boolean;
    hours: number[];       // subset of [8, 12, 17]
    timezone: string;      // IANA timezone, e.g. "America/New_York"
  };
}

// === Scheduled CIBA session type (src/lib/types/scheduled-ciba.ts) ===
interface ScheduledCibaSession {
  batchId: string;               // ISO timestamp of the scheduled run
  userId: string;
  authReqId: string;
  actionIds: string[];
  bindingMessage: string;
  expiresAt: string;             // ISO timestamp
  interval: number;              // poll interval in seconds
  createdAt: string;
}

// === Executor refactoring (src/lib/actions/executor.ts) ===
// Existing (unchanged signature):
export function executeAction(action: SuggestedAction): Promise<ExecutionResult>;
// New export:
export function executeActionWithToken(action: SuggestedAction, token: string): Promise<ExecutionResult>;

// === Data layer: schedule index (src/lib/data/settings.ts) ===
export function updateScheduleIndex(userId: string, oldHours: number[], newHours: number[]): Promise<void>;
export function getUsersForScheduleHour(hour: number): Promise<string[]>;

// === Data layer: scheduled CIBA sessions (src/lib/data/scheduled-ciba.ts) ===
export function storeScheduledCibaSession(session: ScheduledCibaSession): Promise<void>;
export function getScheduledCibaSession(userId: string, batchId: string): Promise<ScheduledCibaSession | null>;
export function getAllActiveScheduledSessions(): Promise<ScheduledCibaSession[]>;
export function removeScheduledCibaSession(userId: string, batchId: string): Promise<void>;

// === Data layer: encrypted refresh token (src/lib/data/schedule-tokens.ts) ===
export function storeScheduleRefreshToken(userId: string, refreshToken: string): Promise<void>;
export function getScheduleRefreshToken(userId: string): Promise<string | null>;
export function deleteScheduleRefreshToken(userId: string): Promise<void>;

// === Crypto (src/lib/crypto.ts) ===
export function encrypt(plaintext: string): string;
export function decrypt(ciphertext: string): string;

// === Settings API extension ===
// PUT /api/settings
// Request Body (new optional field):
// {
//   "schedule": {
//     "enabled": boolean,
//     "hours": (8 | 12 | 17)[],     // max 3 elements
//     "timezone": string              // IANA timezone, max 64 chars
//   }
// }
// Response: UserSettings (with schedule field)

// === Cron Initiate Endpoint ===
// GET /api/cron/schedule-initiate
// Headers: Authorization: Bearer <CRON_SECRET>
```

## Redis Key Design

```
# Schedule preferences — stored within existing settings key
{userId}:settings                              # EXISTING — extended with .schedule field

# Schedule index — enables Phase 1 to find opted-in users by hour
schedule:idx:{hour}                            # Redis SET of userId strings (hour = 8 | 12 | 17)

# Scheduled CIBA sessions
ciba:scheduled:{userId}:{batchId}              # JSON, TTL 600s (10 min)

# Active sessions index — enables Phase 2 to find all outstanding sessions
schedule:ciba:active                           # Redis SET of session keys

# Encrypted refresh token
{userId}:schedule:refresh-token                # AES-256-GCM encrypted, TTL 90 days
```
