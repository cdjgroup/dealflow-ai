# Sherlock Plan: Real-Time Circuit Breaking for AI Tool Execution

## Scope Boundaries
- IN SCOPE:
  - Per-tool per-user rate limiting via Upstash Ratelimit (Layer A — surgical)
  - Per-request tool call abort via AbortController (Layer B — nuclear)
  - Route refactor from `toUIMessageStreamResponse()` to `createUIMessageStream` wrapper
  - Circuit-breaker audit trail entries using existing `writeAuditEntry`
  - Client-side amber error styling for circuit-breaker events
  - Unit tests for circuit-breaker module
  - Route test updates for new stream pattern
- OUT OF SCOPE:
  - Passing `abortSignal` through to tool fetch calls (separate enhancement)
  - Configurable rate limits via UI/settings (hardcoded config for now)
  - MCP endpoint circuit breaking (separate — different execution path)
  - Toast/notification system (use existing inline error display)
  - Per-session rate limiting (per-user per-tool is sufficient)

## Architecture Decision

### Approach chosen: Combined A+C (Pragmatic)

**Summary:** Two-layer circuit breaking — Layer A uses Upstash Ratelimit per-tool for surgical blocking (returns error to model, model can adapt), Layer B uses in-memory counter + AbortController for emergency stream kill (kills entire stream with user-facing error).

**Rationale:** Layer A alone has a blind spot: within a single request the model can make up to `MAX_TOOL_STEPS=7` steps. Layer B alone only protects within a request and resets each time. Combined, they cover cross-request abuse (A) and within-request runaway loops (B). The `createUIMessageStream` wrapper enables clean error messaging before abort — without it, the client sees a silent stream stop with no explanation (server-side abort sends `status: 'ready'`, not error). Upstash Ratelimit adds sub-10ms overhead (single HTTP roundtrip via Lua scripts; ephemeralCache blocks repeated rate-limited calls with zero Redis commands). The in-memory counter adds zero latency.

**Key verified technical facts:**
- Upstash Ratelimit: 1 HTTP roundtrip per `limit()` call via `EVALSHA` Lua scripts. Fixed Window = 2-3 Redis commands, Sliding Window = 3-5 commands. ([Upstash docs](https://upstash.com/docs/redis/sdks/ratelimit-ts/costs))
- `abort()` inside `experimental_onToolCallFinish` works: it fires a signal (doesn't throw), so `notify.ts` error swallowing is irrelevant
- `writer.write()` is synchronous on `createUIMessageStream`'s outer controller — guaranteed to enqueue before `abort()` takes effect
- Server-side `AbortController.abort()` sends clean `{ type: 'abort' }` + `[DONE]` — client sees `status: 'ready'` NOT error. The error chunk we write first overrides this to `status: 'error'`.
- Tools do NOT pass `abortSignal` to fetch — in-flight HTTP requests complete after abort (results discarded). Read tools: harmless. Write tools: already gated by approval+CIBA.
- `createUIMessageStream` `onFinish` fires with `isAborted: true` on abort — conversation save can be guarded.

### Alternatives Considered
1. **Minimal (A only)**: Per-tool Ratelimit wrapper. Simpler but cannot kill a runaway stream within a single request.
2. **Clean (A+C + abortSignal passthrough)**: Also thread `abortSignal` through all 6 tool files' `fetch()` calls. Better abort fidelity but larger scope; primarily protects against read-tool spam where write tools are already gated.

## Acceptance Criteria

### AC-1: Per-tool rate limiting blocks excessive calls
- **Given** a user has called `searchEmails` 10 times in the last 60 seconds
- **When** the AI model attempts an 11th `searchEmails` call
- **Then** the tool returns an error result to the model containing the tool name, limit, and reset time; the original tool execute function is NOT called; an audit entry is written with `result: 'error'`

### AC-2: Per-tool rate limiting allows calls within limits
- **Given** a user has called `searchEmails` 5 times in the last 60 seconds
- **When** the AI model calls `searchEmails` again
- **Then** the tool executes normally and the result is returned to the model

### AC-3: Request-level abort kills stream when threshold breached
- **Given** a streaming chat request where 15 tool calls have already completed
- **When** the 16th tool call finishes via `experimental_onToolCallFinish`
- **Then** an error chunk with circuit-breaker explanation is written to the stream, the AbortController fires, the stream terminates, and an audit entry is written

### AC-4: Client displays circuit-breaker error with amber styling
- **Given** the stream is aborted by the circuit breaker
- **When** the error chunk arrives at the client
- **Then** the chat displays an amber-styled error banner (not red) with the circuit-breaker message, and the input re-enables

### AC-5: Tools without rate limits pass through unchanged
- **Given** `delegateResearch` and `analyzePipeline` are not in the rate limit config
- **When** these tools are called
- **Then** they execute without any rate limit check (zero Redis overhead)

### AC-6: Circuit breaker fails open on Redis errors
- **Given** Upstash Redis is unreachable during a per-tool rate limit check
- **When** the `Ratelimit.limit()` call throws
- **Then** the tool executes normally (fail-open), and the error is logged to console

### AC-7: Existing tool pipeline preserved
- **Given** the circuit breaker is wired into the tool pipeline
- **When** a tool requiring approval or CIBA is called within rate limits
- **Then** the approval and CIBA flows work exactly as before

### AC-8: Conversation persistence on normal completion
- **Given** the route uses `createUIMessageStream` with `onFinish`
- **When** a chat request completes normally (no abort)
- **Then** the conversation is saved to Redis as before

### AC-9: Audit trail captures per-tool blocks
- **Given** a tool call is blocked by the per-tool rate limiter
- **When** the block occurs
- **Then** an audit entry is written with `toolName`, `result: 'error'`, and `errorMessage` containing tier and reset time
