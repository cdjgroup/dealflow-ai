# Sherlock Plan: CIBA-Gated Write Operations for MCP Server
Created: 2026-04-05
Tier: Full Sherlock
Status: APPROVED — Executing

## Scope Boundaries
- IN SCOPE:
  - Register `draftEmail`, `createCalendarEvent`, `sendSlackMessage` on MCP server
  - Gate all MCP write tools with synchronous CIBA approval (Guardian push)
  - Fix all MCP Token Vault tools (read + write) to use stored refresh token instead of session-based `exchangeToken()`
  - Build binding message generator for MCP tool calls
  - Audit logging for all MCP tool executions (already exists, verify it covers new tools)
  - Connection-disabled check for MCP token exchange
- OUT OF SCOPE:
  - CRM write tools on MCP (`createDeal`, `updateDeal`, `createContact`, `logActivity`)
  - MCP agent identity tracking (MCP spec doesn't carry agent metadata)
  - Streaming/SSE for long-polling (synchronous poll is sufficient)
  - UI changes (MCP is headless by design)
  - Modifying existing tool `execute` functions (we bypass them for MCP)

## Architecture Decision

### Approach 1: Minimal — Inline Token Executors in tool-adapter.ts
Add MCP-specific executor functions directly in `tool-adapter.ts` that accept a pre-obtained token. Each executor replicates the fetch logic from the tool files but with `token` as a parameter. CIBA gate runs before execution for write tools.

**Pros:** Self-contained, no changes to existing tool files, clear separation of MCP vs chat execution paths.
**Cons:** ~80 lines of fetch call logic that mirrors existing tool/executor code. Six executors (3 read + 3 write).

### Approach 2: Clean — Token Override Parameter on Tools
Modify each tool's `execute` function to accept an optional `tokenOverride` parameter. If provided, skip `exchangeToken()` and use the override. MCP handler passes the pre-obtained token.

**Pros:** No duplicated API call logic. Single source of truth for each tool's execution.
**Cons:** Modifies 6 existing tool functions (calendar, gmail, slack — read + write). Adds complexity to the hot path used by the chat route. Couples MCP concerns into tool definitions.

### Approach 3: Pragmatic — Hybrid (Reuse executor.ts for writes, inline for reads)
For write tools, map MCP params to the shapes expected by `executeActionWithToken()` in `executor.ts`. For read tools, write thin inline executors (read tools are simpler — just fetch + parse).

**Pros:** Reuses existing write execution logic. Less duplication for the complex cases.
**Cons:** Param shape mismatch — MCP tool params differ from `SuggestedAction` draft shapes (e.g., `createCalendarEvent` uses `startDateTime`/`endDateTime` while `CalendarDraft` uses `date`/`time`/`duration`). Requires adapter code to bridge the shapes, adding complexity without reducing total code.

### Decision
Approach chosen: Approach 1 (Minimal)
Rationale: The duplicated fetch logic is 5-15 lines per executor — straightforward and self-documenting. The alternatives either touch the chat hot path (Approach 2) or require awkward shape-bridging (Approach 3). MCP executors can intentionally diverge from chat behavior (different error messages, no `_tokenMeta`). Avoids modifying working code to serve a new consumer — keeps MCP as a separate execution path with its own error handling.

## Acceptance Criteria

### AC-1: Write tools appear in MCP tool listing
- **Given** an MCP client connects to the server with a valid bearer token
- **When** it requests the list of available tools
- **Then** `draftEmail`, `createCalendarEvent`, `sendSlackMessage` appear alongside existing read tools (9 total tools)

### AC-2: CIBA gate triggers for write tools
- **Given** an MCP client calls `draftEmail` with valid params `{to, subject, body}`
- **When** the tool handler begins execution
- **Then** a CIBA request is initiated via Auth0 `/bc-authorize`
- **And** the binding message follows format "MCP: draft email to {to}" (max 64 chars)
- **And** the handler polls for approval within the request

### AC-3: Approved CIBA completes execution
- **Given** the user approves the Guardian push notification
- **When** `pollCiba()` returns `status: "approved"`
- **Then** the stored refresh token is retrieved via `getScheduleRefreshToken(userId)`
- **And** `exchangeTokenWithRefresh()` obtains a federated access token
- **And** the write operation executes (e.g., Gmail draft created)
- **And** the MCP client receives a success response with operation details

### AC-4: Denied CIBA returns error
- **Given** the user denies the Guardian push notification
- **When** `pollCiba()` returns `status: "denied"`
- **Then** the MCP client receives `{ error: "User denied approval for draftEmail" }` with `isError: true`

### AC-5: CIBA timeout returns error
- **Given** the user does not respond within the polling window (~50 seconds)
- **When** the max wait time is exceeded
- **Then** the MCP client receives `{ error: "Approval timed out for draftEmail" }` with `isError: true`

### AC-6: Read tools use stored refresh token
- **Given** an MCP client calls `checkCalendar` via bearer token auth (no browser session)
- **When** the tool executes
- **Then** it uses `getScheduleRefreshToken(userId)` + `exchangeTokenWithRefresh()` (NOT `exchangeToken()`)
- **And** the tool succeeds without requiring browser cookies

### AC-7: Missing refresh token returns helpful error
- **Given** a user has not opted into scheduled actions (no stored refresh token in Redis)
- **When** they call any Token Vault tool via MCP
- **Then** they receive `{ error: "No stored refresh token. Enable scheduled actions in the app to use MCP tools." }`

### AC-8: Disabled connection returns error
- **Given** a user has disconnected their Google connection via Permissions
- **When** they call `draftEmail` via MCP
- **Then** they receive a connection-disabled error before CIBA is initiated (no unnecessary push notification)

### AC-9: Read tools skip CIBA
- **Given** an MCP client calls `checkCalendar` (a read tool)
- **When** the tool handler begins execution
- **Then** no CIBA approval is requested
- **And** the tool executes directly with the stored refresh token

### AC-10: Audit logging covers all MCP tools
- **Given** any MCP tool call (read or write, success or failure)
- **When** the tool completes
- **Then** an audit entry is written with `threadId: "mcp"`, tool name, input params, result, and duration

### AC-11: Binding messages are descriptive and within spec
- **Given** `draftEmail` called with `{to: "john@acme.com", subject: "Q2 Proposal"}`
- **When** the binding message is generated
- **Then** it equals `"MCP: draft email to john@acme.com"` (or truncated to 64 chars if longer)
- **Given** `createCalendarEvent` called with `{summary: "Pipeline Review"}`
- **When** the binding message is generated
- **Then** it equals `"MCP: calendar \"Pipeline Review\""` (or truncated to 64 chars)
- **Given** `sendSlackMessage` called with `{channel: "deals", text: "Pipeline update..."}`
- **When** the binding message is generated
- **Then** it equals `"MCP: slack #deals \"Pipeline update...\""` (or truncated to 64 chars)

## Interface Contracts

```typescript
// === src/lib/mcp/ciba-gate.ts (CREATE) ===

type CibaGateSuccess = { approved: true };
type CibaGateFailure = {
  approved: false;
  error: string;
  status: "denied" | "expired" | "error" | "timeout";
};
type CibaGateResult = CibaGateSuccess | CibaGateFailure;

/**
 * Synchronously gate MCP tool execution behind CIBA approval.
 * Initiates Guardian push, polls until resolved or timeout.
 * No Redis session storage -- polls within a single request lifecycle.
 */
export async function cibaGate(
  userId: string,
  toolName: string,
  bindingMessage: string,
  maxWaitMs?: number, // default: 50000 (50s, 10s buffer for Vercel 60s limit)
): Promise<CibaGateResult>;

/**
 * Build a binding message for MCP tool calls.
 * Format: "MCP: {action} {key detail}", truncated to 64 chars per CIBA spec.
 */
export function buildMcpBindingMessage(
  toolName: string,
  params: Record<string, unknown>,
): string;

// === src/lib/ciba/should-require.ts (MODIFY -- add export) ===

/** All Token Vault write tools require CIBA when called via MCP. */
export function shouldRequireCibaMcp(toolName: string): boolean;

// === src/lib/mcp/tool-adapter.ts (MODIFY -- internal helpers) ===

/**
 * Get a federated access token for MCP tool execution.
 * Uses stored refresh token (same trust model as scheduled actions).
 * Checks connection-disabled status before exchange.
 */
async function getMcpAccessToken(
  userId: string,
  connection: string,
): Promise<string>; // throws Error on failure

/**
 * MCP-specific tool executors. Accept a pre-obtained access token.
 * Bypass the tool's built-in execute (which calls session-based exchangeToken).
 */
const MCP_EXECUTORS: Record<
  string,
  (params: Record<string, unknown>, token: string) => Promise<unknown>
>;
```
